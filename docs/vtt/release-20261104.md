## Instalacao e dados

1. Codigo enviado para `dev` deve entrar pelo `/site-update` monitorado do bot.
   Nao usar push como evidencia de deploy ou executar comandos remotos avulsos.
2. Migration `0167_vtt_lab` cria somente duas tabelas do laboratorio. Nao e seeder
   de magias, nao substitui PKs e nao reatribui rulesets de personagens.
3. `networkx==3.7` precisa estar disponivel no ambiente Python compativel do
   servidor para caminhada. Ausencia desabilita caminhada explicitamente, sem
   import eager no site; nao presumir que pull instala dependencias.
4. Conferir schema da API e `class-catalog-read` com a chave existente; ler
   fonte/snapshot atuais, refazer plano de concessoes, guardar antes/versoes e
   aplicar apenas o diff confirmado. Publicar nova revisao pelo fluxo existente.
   Preservar personagens legados e suas revisoes.
   O complemento de compatibilidade seleciona ponteiro publicado, depois o mapa
   `CLASS_CATALOG_RULESETS` (incluindo alias da configuracao legada), depois fonte.
   Snapshot selecionado invalido nunca cai na fonte. Nao precisa gerar outra chave.
5. VTT permanece `VTT_LAB_ENABLED=false` por padrao. Ativacao privada requer a
   flag no ambiente e reinicio normal. URL `/vtt/laboratorio/`, somente superuser
   ativo; sem menu publico. Uma sessao pertence exclusivamente ao criador.

## Limites conhecidos

Sem executor completo de conjuracao, LoS/alcance automatico, geometria vertical,
tokens grandes, dash ou multiplayer. Acerto/dano/ordem sao declarados. Tags
opacas/exportadas nao sao prova de efeito automatizado. QA com fichas ficticias
e SQLite isolado nao substitui primeira ficha real ou concorrencia PostgreSQL.

Rollback: desligar a flag e manter saves/recibos para diagnostico. Nao apagar
tabelas, personagens ou conteudo para desfazer o teste privado. Saves de combate
com hash de motor antigo nao sao reinterpretados silenciosamente.
